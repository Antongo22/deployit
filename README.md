# DeployIt

Панель деплоя на **C# / .NET 10 / Blazor Server**. Подключите GitHub или GitLab,
привяжите репозиторий к Linux-серверу по SSH и разворачивайте выбранную ветку одной кнопкой.

## Запуск через Docker Compose

Нужен Docker с Compose. Локальные .NET, Node.js и база данных не требуются.

```bash
docker compose up -d --build --wait
```

Панель: **http://localhost:8080**. Пользователь по умолчанию: **admin**.
При первом запуске создаётся случайный пароль. Получить его:

```bash
docker compose exec app cat /data/admin-password
```

Пароль сохраняется в томе и не меняется при обычном перезапуске.
Swagger доступен после входа: http://localhost:8080/swagger.

Необязательная конфигурация:

```bash
cp .env.example .env
# Отредактируйте .env, затем:
docker compose up -d
```

| Переменная | Значение по умолчанию | Назначение |
| --- | --- | --- |
| `DEPLOYIT_PORT` | `8080` | Порт панели |
| `DEPLOYIT_BIND_ADDRESS` | `127.0.0.1` | Интерфейс публикации порта |
| `DEPLOYIT_ADMIN_USERNAME` | `admin` | Имя администратора |
| `DEPLOYIT_ADMIN_PASSWORD` | пусто | Свой пароль, минимум 12 символов; иначе используется автоматически созданный |

На удалённом сервере панель можно открыть через SSH-туннель:

```bash
ssh -L 8080:127.0.0.1:8080 user@panel-server
```

Для постоянного доступа по домену поставьте перед панелью HTTPS reverse proxy
с поддержкой WebSocket. Порт по умолчанию опубликован только на loopback.

## Подключение проекта

1. В разделе **Git-подключения** добавьте GitHub или GitLab.
   - GitHub: fine-grained token с доступом к выбранным репозиториям, Metadata: Read и Contents: Read.
   - GitLab: personal access token с `read_api` и `read_repository`.
   - Для публичных репозиториев можно включить режим без токена и указать имя аккаунта.
   - Поддерживаются GitHub.com и GitLab.com / собственный GitLab по HTTPS в корне домена.
2. Создайте проект: выберите аккаунт, репозиторий и ветку.
3. Укажите SSH-сервер, порт, пользователя и выберите **Способ входа по SSH**:
   - **SSH-ключ** — вставьте приватный ключ. Его публичная часть должна находиться
     в `~/.ssh/authorized_keys` этого пользователя на целевом сервере.
   - **Логин и пароль** — введите пароль пользователя на сервере. Например, для
     `ssh deploy@app.example.com` пользователь — `deploy`, пароль — его пароль на сервере.
     SSH-сервер должен разрешать вход по паролю.
4. Получите отпечаток ключа сервера и сверьте его на сервере:
   `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`.
5. Укажите отдельный корневой каталог проекта, команду деплоя и команду перезапуска.
6. Сохраните, проверьте SSH и нажмите **Развернуть**.

Один репозиторий и один SSH-адрес (`host:port`) могут принадлежать только одному проекту.
SSH-ключи с паролем поддерживаются. При редактировании пустое поле ключа сохраняет текущий ключ.
При входе по паролю пустое поле пароля сохраняет уже заданный пароль. Чтобы сменить
способ входа, выберите другой вариант и введите новые учётные данные.
Выбранный способ используется для SSH-проверки, деплоя, перезапуска, редактора `.env`,
терминала и SFTP-передачи Git-токена.
При обновлении панели существующие проекты сохраняют вход по ключу; база обновляется автоматически.
Токен подключения можно обновить без пересоздания проектов.

## Что происходит при деплое

- В SQLite создаётся задача со снимком конфигурации. Повторный активный запуск проекта отклоняется.
- Фоновый обработчик последовательно выполняет задачи через SSH.
- На сервере создаётся `<каталог>/releases/<id-запуска>` и клонируется выбранная ветка.
- Сохраняется SHA полученного коммита, затем из каталога кода запускается команда через `bash`.
- stdout и stderr появляются в журнале панели; размер журнала ограничен 1 МБ.
  При превышении лимита сохраняются начало и последние строки, включая итог ошибки.
- Код `0` означает успех. После успеха `<каталог>/current` указывает на новый release.
- При ошибке предыдущая ссылка `current` сохраняется. Старые releases автоматически не удаляются.

Целевой сервер: Linux, SSH/SFTP, `bash`, `git`, `timeout`, `flock` и инструменты,
которые использует ваша команда. SSH-пользователю нужны права на каталог проекта
и запуск этих инструментов. Панель сама не устанавливает Docker на целевой сервер.

Пример команды для приложения с `compose.yaml` в репозитории:

```bash
docker compose up -d --build --remove-orphans --wait --wait-timeout 120
```

Создайте файл окружения через **Редактировать .env** на странице проекта.
Он хранится в корневом каталоге проекта вне `releases`; перед запуском команды
деплоя в release создаётся ссылка `.env` на этот общий файл, если он существует.
Для постоянных данных приложения используйте именованные тома или абсолютные bind-пути:
относительные пути внутри release меняются при каждом запуске.

`--wait` ждёт готовности контейнеров, включая их healthcheck. Без него `up -d`
может вернуть код `0`, даже если приложение сразу после старта упало.
Для DeployIt healthcheck уже задан в `compose.yaml`.

Если разворачиваете сам DeployIt и хотите открыть его по IP сервера, добавьте
в серверный `.env` адрес публикации и свободный внешний порт, например:

```dotenv
DEPLOYIT_BIND_ADDRESS=0.0.0.0
DEPLOYIT_PORT=8010
```

Тогда адрес панели будет `http://<IP сервера>:8010`. Значение `127.0.0.1`
публикует порт только для локального доступа с сервера (например, через reverse proxy).

Dockerfile назначает файлам приложения владельца `app`: это позволяет запускать
образ от непривилегированного пользователя, даже когда исходники клонированы
с `umask 077` и файлы конфигурации имеют права `0600`.

В команду передаются:

- `DEPLOYIT_RELEASE_DIR` — каталог полученного кода;
- `DEPLOYIT_PROJECT_DIR` — корневой каталог проекта;
- `DEPLOYIT_ENV_FILE` — путь к общему серверному `.env`;
- `COMPOSE_PROJECT_NAME` — постоянное имя Compose-проекта, одинаковое для всех его releases.

Таймаут действует на получение кода и выполнение команды. Удалённый `flock` не позволяет
двум запускам пересекаться даже после перезапуска панели. При остановке панели текущий
запуск получает статус «Прерван»: удалённая команда может продолжаться до своего таймаута.
Проверьте сервер перед повторным запуском. Очередь ожидающих задач сохраняется.

### Остановка запуска и ошибки

Кнопка **Остановить** доступна на странице проекта и в заголовке журнала.
Для ожидающей задачи кнопка **Снять с очереди** отменяет запуск до подключения к серверу.
Для выполняющейся задачи запрос сохраняется в SQLite; панель посылает TERM группе
процессов конкретного запуска и, если она не завершилась за 5 секунд, KILL.
Перед отправкой сигнала проверяется, что PID относится к этому запуску.
Нужен Linux с GNU `timeout`, `/proc`, `bash`, `flock` и `tr`.

Во время остановки отображается **Останавливаем…**, новый запуск блокируется.
После подтверждения сервера статус меняется на **Остановлен**. Если SSH недоступен
или завершение процессов подтвердить нельзя, статус будет **Прерван**, а сообщение
попросит проверить сервер. Остановка команды не удаляет уже запущенные контейнеры
и не отменяет выполненные миграции или другие изменения команды.

Над журналом показываются текущий этап, код завершения и блок **Что сломалось**.
При ошибке раскрыты последние 35 строк stdout/stderr. Для таймаута, занятого порта,
нехватки места, отказа в доступе и ошибок сборки предусмотрены пояснения с примерами.
Например, код `124` сообщает о таймауте и предлагает проверить вывод и увеличить
таймаут проекта, если сборке нужно больше времени. Код `137` указывает на KILL:
панель предлагает проверить и таймаут, и возможную нехватку памяти.
В старой истории причина определяется по сохранённым коду и журналу, если отдельной
диагностики ещё нет.

API: `POST /api/deployments/{id}/cancel` (с CSRF-токеном),
`GET /api/deployments/{id}` возвращает `Stage`, `ErrorMessage` и `CancelRequested`.

Сохранение `current` не отменяет побочные эффекты команды: автоматического отката
контейнеров, миграций БД и других изменений в этой версии нет.

## Серверный .env и синхронизация

На странице проекта нажмите **Редактировать .env**. Редактор загружает
`<каталог проекта>/.env` по SFTP; если файла нет, можно создать его сохранением.
Например, для каталога `/opt/apps/my-app` файл будет `/opt/apps/my-app/.env`:

```dotenv
APP_ENV=production
APP_PORT=8000
```

- **Сохранить на сервер** записывает текст атомарно с правами `0600` и обновляет
  ссылку `.env` в текущем release. Запись идёт через стандартный ввод одного
  SSH-соединения; перед заменой файла проверяются контрольные суммы полученного
  текста и исходной серверной версии. Файл сохраняется между деплоями.
- Пока редактор открыт, он проверяет сервер каждые 10 секунд. Изменения с сервера
  автоматически появляются в редакторе, если в нём нет несохранённого текста.
- При конфликте ваш текст остаётся в редакторе, а сохранение отклоняется:
  скопируйте свои изменения, загрузите серверную версию и объедините их.
- Сохранение не перезапускает приложение: для применения нажмите **Перезапустить**.
- Поддерживается UTF-8, до 32 768 символов и 64 КБ. Содержимое `.env` не хранится
  в SQLite и не записывается в журнал панели.

Редактируя файл через SSH, используйте общий путь, например
`nano "$DEPLOYIT_ENV_FILE"`. Редактор синхронизирует именно этот файл.
Файл `.env`, лежащий только в старом release, автоматически не переносится.

Docker Compose использует `.env` для подстановки переменных в `compose.yaml`.
Чтобы передавать переменные внутрь контейнера, укажите `env_file: .env`
у нужного сервиса или перечислите их в `environment`. Например:

```yaml
services:
  web:
    image: my-app:latest
    env_file: .env
    ports:
      - "${APP_PORT}:8000"
```

## Перезапуск

Кнопка **Перезапустить** запускает отдельную задачу с журналом и таймаутом.
Команда выполняется в текущем успешном release без обновления репозитория.
Перед первым перезапуском нужен хотя бы один успешный деплой.

По умолчанию команда такая:

```bash
docker compose up -d --force-recreate --no-build
```

Она пересоздаёт контейнеры из уже имеющихся образов, чтобы применить изменённое
окружение. В настройках проекта можно указать свою команду, например
`sudo -n systemctl restart my-app`. Очередь и блокировка общие с деплоем;
сохранение `.env` также проверяет эту блокировку.

## SSH-терминал

На странице проекта нажмите **Открыть SSH-терминал**. Откроется интерактивная
SSH-сессия с сохранёнными ключом или паролем и проверкой отпечатка сервера.
Поддерживаются Ctrl+C, стрелки, изменение размера окна и интерактивные программы
вроде `nano`, `vim` и `top`, если они установлены на сервере.

Терминал открывается в `current`, а до первого деплоя — в корневом каталоге проекта
или домашнем каталоге пользователя. Передаются `DEPLOYIT_PROJECT_DIR`,
`DEPLOYIT_ENV_FILE` и `COMPOSE_PROJECT_NAME`. Команды имеют права SSH-пользователя.
Закрытие терминала, уход со страницы и истечение сессии панели закрывают SSH-соединение.
Вывод терминала не сохраняется в истории задач.

Терминал использует WebSocket; reverse proxy должен пропускать Upgrade
и исходный заголовок Host. Ресурсы xterm.js включены в приложение и не требуют CDN.

## Данные и доступ

Том `data` содержит SQLite, журналы, пароль первого запуска и ключи ASP.NET Data Protection.
Токены, приватные SSH-ключи и пароли SSH-пользователей зашифрованы в базе и не возвращаются через API.
При клонировании приватного репозитория токен временно передаётся по SFTP в закрытый каталог
на целевом сервере, используется Git askpass и удаляется после запуска.
Известные токены и ключи удаляются из записываемого вывода; произвольные секреты приложения,
которые печатает ваша команда, панель определить не может.

Панель рассчитана на одного доверенного администратора и один экземпляр приложения.
Сохранённая команда имеет права SSH-пользователя. Доступ к тому `data` даёт доступ
к ключам расшифровки, поэтому резервные копии этого тома должны храниться приватно.

```bash
docker compose logs -f app
docker compose restart app
docker compose down
```

`down` сохраняет данные. Не используйте `down -v`, если хотите сохранить проекты,
историю и секреты. Для согласованной резервной копии остановите панель и сохраните
весь том `data`, включая ключи Data Protection и файлы SQLite.

## Проверки через Compose

Тесты правил проекта, защиты секретов, очереди и Linux-скрипта деплоя:

```bash
docker compose --profile test run --build --rm tests
```

Сквозная проверка Blazor в Chromium и настоящего SSH/SFTP на изолированном тестовом сервере:

```bash
docker compose -f compose.yaml -f tests/compose.smoke.yaml up -d --build --wait app ssh-target
docker compose -f compose.yaml -f tests/compose.smoke.yaml run --build --rm smoke
# После проверки можно остановить тестовый SSH-сервер:
docker compose -f compose.yaml -f tests/compose.smoke.yaml stop ssh-target
```

Smoke-тест читает публичный `octocat/Hello-World` с GitHub, создаёт собственные тестовые
подключение и проект, проверяет успешную команду и ошибку, затем удаляет свои записи.
Браузер и SSH-сервер запускаются в отдельных контейнерах. Результат и скриншоты сохраняются
в `artifacts/`. Требуется интернет для NuGet, образов, Chromium и GitHub.

## Структура

- `Components` — страницы и компоненты Blazor;
- `Controllers`, `DTOs` — защищённый HTTP API и публичные контракты;
- `Models`, `Data` — сущности и EF Core / SQLite;
- `Services` — Git API, шифрование, SSH и очередь деплоев;
- `wwwroot` — стили и статические ресурсы;
- `tests` — C# unit-тесты, Playwright-проверка и тестовый SSH-сервер.
